# 要件定義書（詳細版） — Geniesta

> OSS ライブラリ/リポジトリを、star でなく「信頼できるか」に関わる**公開事実**で選べる**汎用**ツール。判定はせず、出典つきの事実を選定の瞬間に集約する。

---

## 1. 背景・課題

1. 開発者は日常的に OSS ライブラリ/依存を選ぶ。だが「放置されていないか・脆弱性対応は速いか・メンテナは生きているか」を**選ぶ瞬間に**確認する手段が無く、放置/脆弱な依存を掴む事故につながる。
2. 実際の発見手段（GitHub検索）は **star＝人気順**。**人気 ≠ 信頼性**。star が多くても、放置・脆弱性対応が遅い・単独メンテナは普通にある。
3. 信頼性の材料（脆弱性履歴と修正の速さ・生存性・SECURITY.md・bus factor）は既存ツール（Scorecard / Snyk / Socket / OSS Insight）にあるが、**「名指ししたパッケージを採点する/分析する」段階**のもので、**"選ぶ瞬間"から切り離されてる**。

**立ち位置**: スコアリングの発明ではない。空いてるのは「信頼性に関わる事実を**選定の瞬間に**集約し／**出典**を見せる」こと。**特定ジャンルに限定しない汎用ツール**（暗号/セキュリティ等の高 stakes な依存で特に効くが対象は全 OSS）。

## 2. ターゲット・提供価値

- **ターゲット**: OSS ライブラリ/依存を採用・更新しようとする開発者全般
- **提供価値**: 「10タブ開いて手作業で評価」を、選ぶその場で**根拠つきの事実比較**に変える

## 6. 信頼評価ロジック（中立事実版）

判定・単一スコアは出さない。各軸の**生の事実＋出典**を提示し、解釈は利用者に委ねる。

**信頼ファクトは 4 軸**（当初の「実使用＝DL推移」軸は、保守性・信頼性が価値に見合わないと判断し撤去。経緯は README「振り返り」）。

| 軸 | 提示する事実 | データ源 |
|----|------|------|
| 生存性 | 最終コミット/リリース日・リリース頻度・月次コミット推移 | GitHub REST/GraphQL |
| 脆弱性 | **未修正の有無・CVSS・修正までの時間**（生件数でなく） | GitHub Advisory(GHSA) ＋ OSV クロスチェック |
| 姿勢 | SECURITY.md / 開示ポリシー・行動規範等の有無・community health | community profile API |
| メンテナ集中 | 活発なメンテナ数・トップ貢献者の占有率 | contributors API |

- 注意喚起の表示までは可。**蔑称的ラベル・善悪判定はしない**。
- 脆弱性は「件数」でなく「**未修正があるか × 修正の速さ**」で読む（CVE履歴自体は中立〜健全）。
- **no-data ≠ safe（F-11）**: データ取得失敗・repo→package 未解決を「確認済み 0」と**同一視しない**。状態を分けて表示し、偽りの安心を防ぐ。
- **バージョン特定（F-12）**: 脆弱性は対象バージョンを明示（最新/指定）。repo 単位の曖昧さを採用判断に持ち込まない。
- 追加で扱う事実（補強 / EXT）: ライセンス(F-13)・第三者監査歴(F-27)・署名/provenance(F-28)・依存の健全性(F-29)・なりすまし注意(F-30)。いずれも**事実＋出典**まで（判定しない）。

## 7. データ要件・API

| 機能 | API |
|------|-----|
| 検索・基本情報・詳細 | GitHub REST（search/repositories, repos, contributors, community/profile） |
| 脆弱性 | GitHub Advisory DB（GraphQL `securityVulnerabilities`）＋ OSV（api.osv.dev）クロスチェック |
| レジストリ検索（名前 → GitHub リポ解決） | 各レジストリの公開 API（npm / crates / Packagist / Hex / NuGet / pub）。機能 8・準備中 6（公開検索 API が無いものは UI 表示のみ） |
| ライセンス | GitHub（SPDX）＋ manifest 宣言・LICENSE 本文のフォールバック |

**注意**: 脆弱性は「ecosystem＋パッケージ名」で紐づく。検索が返すのは「リポジトリ」なので、**repo → パッケージ名の解決**（manifest から推定・レジストリ経由）が必要。限界は明記する。GHSA 対応は npm・crates。

## 10. 技術スタック

- **フロント**: Next.js v16+（App Router・RSC）/ React 19 / TypeScript(strict) / Tailwind v4 / shadcn/ui
- **データ取得**: サーバー側（Server Component / Route Handler）。**外部 4 ベンダー＝GitHub REST+GraphQL / OSV / npm / crates**（＋検索 API が堅いレジストリ）。token はサーバー側のみ。
- **アーキテクチャ**: Next.js 単体（別建て BFF/DB なし）。クリーンアーキの層分離（`lib/types`→`lib/use-cases`→`lib/server`、`server-only` 境界をコンパイラ強制）。ISR（`unstable_cache`/revalidate）＋サーキットブレーカ・single-flight・graceful degradation。
- **テスト**: Vitest + Testing Library + MSW（ユニット/コンポーネント）、Playwright+axe（E2E）、jest-axe（a11y）、契約テスト（実 API・nightly）、ミューテーション（Stryker・ドメイン純関数）
- **CI**: GitHub Actions（型→Lint→カバレッジゲート→build→E2E、fail-fast）。契約テストは nightly で分離。

## 11. テスト戦略（フェーズ別）

| Phase | 層 | 内容 |
|-------|----|------|
| 0 | 静的 | `tsc --noEmit`（strict）＋ Lint（react-hooks / jsx-a11y） |
| 1 | ユニット | ドメイン純関数（trust/version/licenses/search-query…の境界・異常系）＋ ゲートウェイ（MSW で レート制限・404・500・縮退） |
| 2 | コンポーネント | 検索バー・結果カード・フィルタ・比較・状態表示 ＋ a11y（jest-axe） |
| 3 | E2E | 検索→一覧→**詳細ページ遷移**（モーダルでない事を URL で保証）・比較・依存チェック・キーボード/axe。網はモック or 実起動 |
| 4 | 契約 | 実 GitHub/OSV に当て、依存するレスポンスのフィールド存続を検証（MSW が隠す契約ドリフト対策・nightly） |
| 5 | ミューテーション | Stryker をドメイン純関数に限定し、同語反復テストを裏取り |
| 6 | CI | Phase 0-3 を Actions で fail-fast。契約・ミューテーションは nightly/ローカル |

配分思想: **実行境界とバグの所在で配分**（形＝ピラミッド/トロフィーは争わない）。ドメイン純関数は unit で厚く、状態を持つ画面は component が重心、非同期 RSC は E2E へ逃がす。E2E は重要ジャーニーとブラウザ必須の関心のみ。

## 12. 受け入れ基準

| ID | 基準 |
|----|------|
| AC-1 | 放置リポジトリ → 「最終リリースが古い」事実が出典つきで提示 |
| AC-2 | 未修正脆弱性あり → 「未修正あり＋CVSS＋修正の速さ」を提示 |
| AC-3 | 単独メンテナ → 「活発なメンテナ数」「SECURITY.md 有無」を提示 |
| AC-4 | star と DL 数の乖離 → 両方併記され乖離が分かる |
| AC-5 | 全提示事実に出典リンクがある |
| AC-6 | AI キー未設定でも全機能が壊れず動作（graceful degradation） |
| AC-7 | 詳細はモーダルでなく独立ページ（URL 遷移で確認） |
| AC-8 | データ取得不可/未解決の事実は「**データ無し**」と明示され、「確認済み 0」と区別される（F-11） |
| AC-9 | 脆弱性の事実に**対象バージョン**が表示される（F-12） |
| AC-10 | 各リポに**ライセンス**が表示され、無い場合は「不明」と明示される（F-13） |
| AC-11 | 詳細から install/docs/レジストリへの導線がある（F-16）。各事実に**鮮度（取得時刻）**が分かる（F-15） |

## 13. 決定済み（当初の未決事項 → 現在の結論）

1. **対象エコシステムの範囲** → GitHub ＋ 検索 API が堅い 8 レジストリを機能実装、残り 6 は「準備中」表示（信頼性の線引き）。
2. **第2API（deps.dev / DL数）の採用** → **見送り**。保守性・信頼性が価値に見合わず撤去し、脆弱性は OSV クロスチェックで二重化（外部ベンダー 約20→4）。
3. **成果物の到達点** → 動く実装（検索→詳細・比較・依存チェック）＋運用設計（reliability/ops）＋テスト一式（unit/component/E2E/契約/ミューテーション）。
4. **正式名称** → **Geniesta**（確定）。
